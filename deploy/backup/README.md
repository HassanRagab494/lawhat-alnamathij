# النسخ الاحتياطي والاستعادة والتراجع — لوحة النماذج

> خاص بمورد `lawhat-alnamathij` فقط. لا يمس قواعد أو ملفات أو volumes أي مشروع آخر.

## ما يُنسخ وكيف

خدمة `backup` في `compose.production.yaml` (الصورة `deploy/backup/Dockerfile`) تشغّل `schedule.sh`.

**الجدولة:** يوميًا الساعة **02:30 بتوقيت الرياض**، ويمكن تغييرها بـ `BACKUP_TIME`.

**الاحتفاظ:** **7 نسخ يومية** و**4 أسبوعية**:

- الأسبوعية رابط صلب لنسخة الجمعة، أي `WEEKLY_DAY=5`.
- الحذف يتم فقط بعد نجاح النسخة الجديدة.
- الحذف داخل `/backups/daily` و`/backups/weekly` فقط، ولمجلدات بنمط `YYYYMMDDTHHMMSSZ` فقط.

**محتوى كل نسخة** (`/backups/daily/<الوقت>/`):

| الملف                | المحتوى                                                                            |
| -------------------- | ---------------------------------------------------------------------------------- |
| `db.sql.gz.enc`      | `mysqldump --single-transaction` لقاعدة `lawha`، مضغوط ومشفر                       |
| `uploads.tar.gz.enc` | مجلد `files` من volume الملفات                                                     |
| `attached.tsv.enc`   | قائمة الملفات المرتبطة بردود: مفتاح التخزين، SHA-256، الحجم                        |
| `manifest.json`      | وقت النسخة، وعدد الملفات المرتبطة والمؤرشفة، وحجم كل أرشيف مشفر وتجزئته. بلا أسرار |
| `SHA256SUMS`         | تجزئات كل ما سبق؛ الاستعادة ترفض أي اختلاف                                         |

**التشفير:** `openssl aes-256-cbc` مع PBKDF2 (200000 تكرار).

- المفتاح في متغير Coolify السري `BACKUP_ENCRYPTION_KEY`، ولا يُطبع ولا يُمرَّر في سطر الأوامر.
- **احفظ نسخة من المفتاح خارج الخادم.** دونه لا يمكن استعادة أي نسخة.

**الحالة:** آخر نتيجة في `/backups/last-status.json`: الوقت، و`ok`، والمدة، ورسالة قصيرة بلا أسرار.

### الاتساق بين القاعدة والملفات

1. يُنفَّذ `mysqldump --single-transaction` أولًا، فتكون القاعدة لقطة متسقة.
2. بعد انتهائه تُقرأ قائمة الملفات المرتبطة بردود. القائمة تحوي كل ما في اللقطة وأكثر.
3. ثم يُؤرشف مجلد الملفات.
4. ملفات الردود **لا تُعدَّل ولا تُحذف أبدًا**؛ التنظيف يمس الملفات المؤقتة غير المرتبطة فقط. لذلك كل ملف يشير إليه رد في اللقطة موجود وقت الأرشفة.
5. قبل اعتماد النسخة يُتحقق أن **كل** ملف في القائمة موجود في الأرشيف وتجزئته تطابق القاعدة. أي نقص يُفشل النسخة ولا تُعتمد، ويُسجَّل `ok:false`.

جُرّب فعليًا: نسخة لقاعدة فيها 9 ملفات مرتبطة، مع مجلد ملفات فارغ، فشلت برسالة `attached file missing from archive`.

## الإعداد لمرة واحدة

1. **حساب القراءة:** من Terminal خدمة `mysql`، نفّذ [`create-backup-user.sql`](create-backup-user.sql) بحساب root بعد وضع كلمة قوية.
   - الصلاحيات `SELECT, SHOW VIEW, TRIGGER` على `lawha.*` فقط.
2. **متغيرات Coolify السرية:**
   - `BACKUP_DB_PASSWORD`: الكلمة نفسها.
   - `BACKUP_ENCRYPTION_KEY`: 64 محرفًا عشوائيًا، مثلًا ناتج `openssl rand -hex 32` على جهازك. احفظه خارج الخادم أيضًا.
3. **التحقق بعد النشر:** من Terminal خدمة `backup`:
   ```bash
   /opt/lawha-backup/backup.sh && cat /backups/last-status.json
   ```

## اختبار الاستعادة (إلى قاعدة وتخزين منفصلين، دون لمس الإنتاج)

الأداة [`restore.sh`](restore.sh) ترفض دائمًا:

- قاعدة هدف اسمها `lawha`.
- مجلد هدف هو `/data/uploads`.
- مجلد هدف غير فارغ.
- نسخة تختلف تجزئاتها.
- مفتاحًا خاطئًا.

بعد الاستيراد تتحقق من:

- عدد المستخدمين والنماذج والإصدارات والردود والإجابات والملفات.
- سلامة العلاقات: رد بإصدار من النموذج نفسه، إجابة بسؤال من إصدار الرد، ملف بإجابة ورد مطابقين.
- وجود كل ملف مرتبط في التخزين المستعاد، ومطابقة تجزئته.

**على الخادم:**

1. من Terminal خدمة `mysql` بحساب root، أنشئ قاعدة مؤقتة وحسابًا لها:
   ```sql
   CREATE DATABASE lawha_restore_test;
   CREATE USER 'lawha_restore'@'%' IDENTIFIED BY '<كلمة مؤقتة>';
   GRANT ALL ON lawha_restore_test.* TO 'lawha_restore'@'%';
   ```
2. من Terminal خدمة `backup`:
   ```bash
   RESTORE_DB_HOST=mysql RESTORE_DB_NAME=lawha_restore_test RESTORE_DB_USER=lawha_restore \
   RESTORE_DB_PASSWORD='<الكلمة المؤقتة>' RESTORE_UPLOAD_DIR=/tmp/restore-test \
   /opt/lawha-backup/restore.sh /backups/daily/<أحدث مجلد>
   ```
   النتيجة المطلوبة: `restore verified OK`.
3. التنظيف:
   - `rm -rf /tmp/restore-test` في حاوية backup.
   - في mysql:
     ```sql
     DROP DATABASE lawha_restore_test;
     DROP USER 'lawha_restore'@'%';
     ```

**ما اختُبر محليًا (لم يُنفذ على الخادم بعد):**

1. نسخ قاعدة الاختبار مع 3 ردود و9 ملفات مرتبطة.
2. استعادتها إلى قاعدة منفصلة ومجلد جديد. النتيجة `restore verified OK`، والعلاقات سليمة، و9/9 تجزئات متطابقة، وملف PNG المستعاد يفتح.
3. بعد الاستعادة لم يتغير المصدر: `CHECKSUM TABLE` وتجزئات الملفات كما هي.

الحالات المرفوضة كما يجب:

| الحالة            | الرسالة                                  |
| ----------------- | ---------------------------------------- |
| اسم قاعدة الإنتاج | `target database name equals production` |
| مفتاح خاطئ        | `cannot decrypt`                         |
| أرشيف مُعدَّل     | `checksum mismatch`                      |

## نسخة خارج الخادم

النسخ في volume على الخادم نفسه **لا تحمي من فقد الخادم**. لا توجد وجهة خارجية مصرح بها حاليًا، وهذا **بند مفتوح يحتاج قرار المالك**: مثلًا تخزين S3 أو جهاز آخر.

إلى أن يُحسم القرار، يمكن نسخ أحدث مجلد يدويًا إلى جهاز موثوق، فهو مشفر:

```bash
docker cp <backup-container>:/backups/daily/<الوقت> ./
```

## النسخة قبل تحديث الاستضافة (إلزامي قبل نشر المرحلة النهائية)

حاوية `backup` غير موجودة في النسخة المنشورة حاليًا، ولا توجد ملفات مرفوعة بعد، فتكفي نسخة القاعدة. من الخادم بحساب المسؤول:

```bash
mkdir -p /root/lawha-predeploy && chmod 700 /root/lawha-predeploy
docker exec <mysql-container> sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --no-tablespaces --set-gtid-purged=OFF lawha' \
  | gzip > /root/lawha-predeploy/lawha-$(date -u +%Y%m%dT%H%M%SZ).sql.gz
gzip -t /root/lawha-predeploy/*.sql.gz && ls -l /root/lawha-predeploy
```

- `<mysql-container>`: اسم حاوية mysql لهذا المورد فقط، من `docker ps`. تأكد أنه للمورد `lawhat-alnamathij`.
- كلمة root تُقرأ من متغير البيئة داخل الحاوية، فلا تظهر في سجل الأوامر.

## خطة التراجع (تحافظ على البيانات)

الـ migration النهائية `20261025000000_file_uploads` **إضافية فقط**: جدولان جديدان، وقيمة صلاحية جديدة في الـ enum. **لا تُعكس** ولا يُحذف شيء. إعادة الصورة القديمة وحدها لا تكفي، لأن:

1. الكود القديم لا يعرف قيمة الصلاحية `RESPONSES_FILES_DOWNLOAD`. إن مُنحت لمشرف فسيفشل تحميل صلاحياته. قبل التراجع:
   ```sql
   DELETE FROM user_permissions WHERE permission = 'RESPONSES_FILES_DOWNLOAD';
   ```
   يُعاد منحها بعد العودة للنسخة الجديدة.
2. الكود القديم يرفض أي إجابة لسؤال ملفات. **أغلق الاستقبال** في النماذج التي فيها سؤال ملفات قبل التراجع، حتى لا يواجه الزوار أخطاء.
3. الملفات والردود تبقى في القاعدة والـ volume كما هي، ولا يحذف التراجع شيئًا. عند الرجوع للنسخة الجديدة تعود كاملة.

**طريقة التراجع:**

- من Coolify: Deployments ثم Rollback إلى نشر سابق، أو إعادة نشر commit المرحلة الرابعة `96ebcef`.
- `migrate deploy` في الصورة القديمة لا يفعل شيئًا مع migration أحدث مسجلة.
- تُوقف خدمتا `clamav` و`backup` الجديدتان فقط إن لزم، **دون حذف volumes**.

**إن فشلت الـ migration أثناء النشر:**

- لا تُعتمد الخدمة: فحص صحة `api` يفشل، فلا تبدأ `web`.
- لأنها إضافية، الحل إصلاح السبب وإعادة النشر.
- لا `migrate reset` ولا `db push`.
- عند الضرورة القصوى، الاستعادة من نسخة ما قبل النشر **إلى قاعدة منفصلة أولًا** للتحقق، ثم قرار صريح من المالك.
