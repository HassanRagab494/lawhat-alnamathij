# حدود الثقة لعنوان IP العميل

> **نتيجة عبر الوكيل الفعلي (2026-10-14):** نُفذ `scripts/check-forwarded-for.mjs --base https://forms.flowmaxsa.cloud` من خارج الخادم ⇒ **PASS** للدخول والإرسال (429 في الطلب الحادي عشر رغم ترويسة مزيفة متغيرة)، والمنافذ 3000 و4000 و3306 و3310 مغلقة من الخارج. يبقى مفتوحًا: إثبات أن عنوان كل زائر لا يتحول إلى IP واحد يحتاج عميلًا ثانيًا من شبكة أخرى (انظر آخر الملف). لم يُغيَّر أي إعداد في Coolify أو الوكيل.

## المشكلة

حدّا الدخول وإرسال الردود يُحسبان لكل عنوان IP. يقرأ Express العنوان من `req.ip`، ويحسبه من `X-Forwarded-For` عندما يكون المتصل المباشر بالـ API ضمن `TRUST_PROXY`.

Next.js 15 يمرر الترويسة كما وصلته في الطلبات التي يحولها إلى `/api/*`. عنوان من اتصل به يُكتب فقط إن غابت الترويسة (`x-forwarded-for ??= socket.remoteAddress` في `next/dist/server/base-server.js`).

لا توفر Next.js 15 عنوان الاتصال للـ middleware ولا لـ route handlers. لذلك لا يستطيع التطبيق وحده تمييز ترويسة كتبها الزائر عن ترويسة كتبها وكيل.

**القياس المحلي** (`node scripts/check-forwarded-for.mjs --base http://localhost:3000`)، مع ترويسة مزيفة مختلفة في كل طلب:

| الحد         | النتيجة                       | الحالة |
| ------------ | ----------------------------- | ------ |
| إرسال الردود | 11 طلبًا كلها 404، دون أي 429 | FAIL   |
| تسجيل الدخول | 11 طلبًا كلها 401، دون أي 429 | FAIL   |

أي أن من يصل إلى Next.js مباشرة يتجاوز الحدين.

## مسار الطلب وحدود الثقة المطلوبة

```text
الزائر ──► الوكيل الأمامي (Traefik) ──► Next.js (web) ──► الـ API ──► MySQL
     غير موثوق   │ يستبدل X-Forwarded-For      │ يمرر الترويسة كما هي   │ يثق بـ Next.js فقط
                 │ بعنوان الاتصال الفعلي       │                       │ (TRUST_PROXY)
```

1. **الوكيل الأمامي هو المدخل العام الوحيد**، ويستبدل `X-Forwarded-For` بعنوان الاتصال الفعلي ولا يقبل قيمة الزائر. في Traefik:
   - لا تُستخدم `forwardedHeaders.insecure=true`.
   - لا يُضاف إلى `forwardedHeaders.trustedIPs` أي مصدر يصل إليه الزائر.
   - إن وُضعت أمامه CDN، تُضاف نطاقاتها المنشورة فقط، ويُراجع أن CDN نفسها تستبدل الترويسة.
   - يُكتب الإعداد صراحة في ملف الإعداد، ولا يُعتمد على القيم الافتراضية.
2. **Next.js لا يُنشر على منفذ عام في المضيف.** يصل إليه الوكيل الأمامي وحده عبر شبكة Docker داخلية؛ لا يُكتب `ports:` ولا يُفتح منفذ 3000 في الجدار الناري.
3. **الـ API لا يُنشر إطلاقًا:** بلا router في Traefik وبلا منفذ في المضيف، ويصل إليه Next.js وحده عبر شبكة داخلية خاصة بالخدمتين. `API_ORIGIN` في الواجهة يشير إلى اسم الخدمة الداخلي.
4. **`TRUST_PROXY` في الـ API = عنوان Next.js أو شبكته الداخلية فقط**، مثل شبكة Docker مخصصة للواجهة والـ API بعنوان ثابت معروف. التحقق في `apps/api/src/config/trust-proxy.ts` ويطبق ما يلي:

   | القيمة                                                                     | متى تُرفض                                                                   |
   | -------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
   | `TRUST_PROXY` غير مضبوط                                                    | في الإنتاج: يجب ضبطه صراحة                                                  |
   | `true` و`*` والشبكات الشاملة (`0.0.0.0/0` و`::/0`) والشبكات الأوسع من `/8` | دائمًا: كل متصل يصبح موثوقًا                                                |
   | `false`                                                                    | دائمًا: كل الزوار يظهرون بعنوان Next.js، فيصبح حد كل IP حدًا مشتركًا للجميع |
   | عدد القفزات                                                                | في الإنتاج: يثق بأي متصل مباشر بالـ API دون التحقق من عنوانه                |

### لماذا يكفي هذا لحساب العنوان الصحيح لكل زائر

- يستبدل الوكيل الأمامي الترويسة، فتصل إلى Next.js بقيمة واحدة: عنوان الزائر الحقيقي.
- Next.js يمررها دون إضافة.
- الـ API يرى المتصل المباشر (Next.js) ضمن `TRUST_PROXY`، فيأخذ العنوان من الترويسة.

يبقى لكل زائر عنوانه وحده؛ لا يُعامَل كل الزوار كعنوان واحد. حتى لو أضاف الوكيل العنوان الحقيقي بعد قيمة الزائر بدل الاستبدال، يأخذ Express أقرب عنوان غير موثوق من اليمين، وهو العنوان الحقيقي. هذا صحيح ما دام عنوان الزائر خارج `TRUST_PROXY`. الاستبدال هو المطلوب لأنه لا يعتمد على هذا الشرط.

## الإعداد الصريح في ملفات النشر

ملف [`compose.production.yaml`](../compose.production.yaml) يطبق البنود 2 إلى 4:

- لا `ports:` لأي خدمة.
- `api` و`mysql` على شبكة `backend` الداخلية فقط (`internal: true`).
- `web` يصل إلى الـ API باسم مستعار معرّف على `backend` وحدها.
- `TRUST_PROXY` = `BACKEND_SUBNET`.

البند 1، أي إعداد الوكيل المشترك، يتحقق منه المسؤول دون تعديله في هذه المهمة. التفاصيل في [deploy/coolify/README.md](../deploy/coolify/README.md).

## الاختبار عبر الوكيل الفعلي (نُفذ 2026-10-14 ⇒ PASS)

بعد إعداد الوكيل الأمامي الفعلي، ومن جهاز خارج الخادم:

```bash
node scripts/check-forwarded-for.mjs --base https://forms.flowmaxsa.cloud
```

- **شرط النجاح:** `PASS` للسطرين (ظهور 429 خلال 11 طلبًا لكل حد) وكود خروج 0.
- **الوصول المباشر يجب أن يفشل:** محاولة الوصول من الخارج إلى منفذ Next.js (3000) أو الـ API (4000) على عنوان الخادم يجب أن تفشل في الاتصال.
- السكربت يستهلك حصة الجهاز من الحدين لمدة دقيقة، ولا يُنشئ ردودًا، ولا يقفل حسابات حقيقية لأنه يستخدم أسماء عشوائية غير موجودة.

حد إرسال الردود لكل نموذج (`PUBLIC_SUBMIT_PER_FORM_PER_MINUTE`) مفتاحه `publicId` ولا يتأثر بأي ترويسة، فيبقى سقفًا في كل الأحوال. الإيقاف المؤقت للحساب بعد محاولات الدخول الفاشلة لا يعتمد على IP.

## اختبار «لكل زائر عنوانه» (مطلوب بعميلين)

من جهاز أول: شغّل السكربت حتى يظهر 429. خلال الدقيقة نفسها، من جهاز على **شبكة أخرى** (مثل جوال على بيانات الهاتف): افتح صفحة الدخول وجرّب دخولًا خاطئًا واحدًا ⇒ يجب أن يظهر «بيانات الدخول غير صحيحة» لا «عدد الطلبات كبير». لو ظهرت رسالة الحد فالعنوان يتحول لعنوان واحد للجميع. لم يُنفذ بعد (NOT_RUN): يحتاج جهازًا ثانيًا من المالك.
