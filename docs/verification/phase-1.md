## نطاق التغييرات

- حماية reset في `apps/api/test/database-safety.js`: تحليل MySQL URL، تطبيع المضيف والمنفذ الافتراضي 3306 واسم القاعدة، وإهمال اختلاف بيانات الدخول في تحديد الهوية. رفض الصيغ الغامضة والمعاملات غير المعروفة أو التي قد تغير الوجهة. مقارنة المضيف وعناوين DNS والمنفذ والقاعدة، مع رفض محافظ لأي تطابق في اسم القاعدة حتى عبر منافذ أو مضيفين مختلفين. رفض التعارض مع shadow database أيضًا.
- إلزام اسم ينتهي بـ `_test` و`ALLOW_TEST_DATABASE_RESET` يساوي الاسم، مع بقاء الموافقة فارغة في `.env.example`. يلزم DATABASE_URL صالحًا للمقارنة؛ فشل DNS يرفض التشغيل. لم يُنفذ أي reset أو migration أو إنشاء مستخدم فعلي.
- حدود الهوية: DNS لا يكشف كل أسماء الخادم أو NAT أو الأنفاق، وقد تتغير الإجابات بعد الفحص. لا تُعد هذه الحماية إثباتًا لهوية الخادم الفيزيائي. يجب تخصيص حساب لا يملك صلاحية خارج قاعدة الاختبار والتحقق من الوجهة قبل الموافقة. رفض الاسم المطابق عبر كل المضيفين مقصود ولو كانت قواعد مستقلة فعلًا.
- التعديل والأرشفة والاستعادة تقفل سجل `forms` أولًا بـ `SELECT ... FOR UPDATE`، ثم تُقرأ الحالة وتُعدّل المسودة في المعاملة نفسها. لا توجد قراءة consistent snapshot قبل أخذ القفل في مسار التعديل. الأرشفة التي تفوز بالقفل تجعل التعديل التالي يُرفض بـ FORM_ARCHIVED؛ وإذا فاز التعديل يُعتمد قبل الأرشفة.
- فشل revision ينهي المعاملة ثم يقرأ النسخة الحالية عبر استعلام مستقل قبل إنشاء REVISION_CONFLICT. اختبارات الوحدة تميّز نسخة المعاملة القديمة من قراءة ما بعدها. اختبار التكامل يقارن revision والعنوان والوصف للطلب الخاسر بنتيجة الفائز.
- إعادة محاولة تعارض MySQL/deadlock في معاملات جديدة بحد أقصى 3 محاولات؛ بعد استنفادها تعاد WRITE_CONFLICT. اختُبر تكرار المحاولة وحدها الأقصى.
- الواجهة تحتفظ بالعنوان والوصف عند تعارض المراجعة حتى اختيار المستخدم. اختُبر مسار الإبقاء على التعديلات ومسار تحميل نسخة الخادم على مكونات React الفعلية مع API وهمي.
- فشل الخروج يُبقي المستخدم وحالته، ويعرض رسالة عربية ويعيد تفعيل الزر لإعادة المحاولة. النجاح أو 401 للجلسة المنتهية يسمح بالخروج. اختبارات المكونات تستخدم AuthProvider وAppShell وطلب fetch الوهمي؛ لا تدّعي إثبات MySQL.

## إضافة: حذف المشرفين — 2026-10-13

بطلب المستخدم: «اعمل انه يقدر يعدل او يحذف مشرفين». التعديل (الاسم والصلاحيات والتفعيل وكلمة المرور) كان موجودًا؛ أضيف:

- **حذف ناعم** عبر `DELETE /api/users/:id` (مدير النظام فقط، CSRF مطلوب): `deleted_at` و`deleted_by_id` في `users` (migration `20261013000000_user_soft_delete`)، تعطيل الحساب وإبطال جلساته بسبب `user_deleted`، وتسجيل `user.deleted`. الحساب المحذوف يُعامل كغير موجود في الدخول والقوائم والتفاصيل والإحصاءات، ولا يمكن تفعيله. لا حذف فعلي للصف حتى لا تنكسر علاقات النماذج وسجل العمليات؛ اسم المستخدم يبقى محجوزًا.
